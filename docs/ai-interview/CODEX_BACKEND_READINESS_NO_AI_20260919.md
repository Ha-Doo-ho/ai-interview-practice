# Codex 명령 — AI 미연동 상태의 백엔드 준비·검증

사용자가 확정한 목표: 프론트엔드 담당자는 화면을 먼저 만들고 있다. 지금은 실제 AI를 연동하지 않고, 현재 백엔드의 연결 준비와 검증을 마친다.

이 파일을 프로젝트에 넣고 아래 명령을1→4 순서로 각각 실행한다. 기존6개 문서 후속 명령의 재실행이 아니다. 각 명령은 자신에게 배정된 산출물까지 완성하고 종료한다. 다음 명령을 자동 시작하거나 여러 항목을 일괄 성공으로 처리하지 않는다.

## 공통 범위와 판정 규칙

- 현재 프로젝트 소스·적용 AGENTS.md·기존 테스트를 기준으로 한다. 과거 패키지의 코드 사본을 최신 앱에 덮어쓰지 않는다. 작업 중인 변경을 보존한다.
- 이번에 수정 가능한 범위는 백엔드 준비에 필요한 문서·테스트와 근거가 확인된 최소 백엔드 오류 수정이다. 프론트엔드 파일, 실제 AI 연동·외부 모델 호출, 운영/기존 개발 DB 데이터, 배포는 범위에 포함하지 않는다. 기존 mock은 유지하고 실제 AI 결과처럼 표현하지 않는다.
- 완료 조건·게임 중 분석 허용·정보 공개·입력 상한 등 제품 정책과 API 호환성을 바꾸는 작업은 임의 수행하지 않는다. 현행 동작·기존 요구와의 차이·영향·선택사항을 기록한다. 필요한 부분만 보류하고 독립 작업은 끝낸다.
- 산출물은 `docs/ai-interview/backend-readiness/<실행시각>/`에 모은다. 명령1은 정확한 새 경로를 출력하고 나머지 명령은 그 경로를 사용한다. 실행 폴더가 모호하면 경로·내용으로 식별하고 서로 다른 실행을 섞지 않는다.
- 결과에는 검사 ID, 목적/근거, 입력, 기대값, 실제값, 판정, 실행 방식, 남은 조건을 구분한다. 문서 확인·순수 함수·실제 라우터·DB 확인을 서로 대신하지 않는다. 실행하지 않은 검사는 통과로 세지 않는다.
- H-03은 과거 원본의 국소 보류다. 이번 백엔드 작업의 중단 조건이 아니다. PKG-01/02는 후속 보완 완료 보고가 있으므로 관련 최신 기록을 확인하고 같은 수정을 반복하지 않는다. 새17개 기능 구현이나 세 CSV 전면 재감사·과거 ZIP 재패키징으로 범위를 늘리지 않는다.

## 명령 1 — 현재 백엔드와 안전한 실행 조건 확인

```text
[명령 1/4: 기준과 실행 환경]
CODEX_BACKEND_READINESS_NO_AI_20260919.md의 공통 규칙과 적용 AGENTS.md를 읽고 이번 백엔드 준비 폴더를 생성하라. 현재 코드, 기존 테스트, 실행 설정, 최신 검토 기록을 찾아 경로·소스 버전·관련 해시를 기록한다. 프론트는 별도 담당의 화면 우선 개발이며 AI 미연동이 이번 전제다.

1-A. 등록된 API, 인증·세션, 회차 상태, 설문·게임·답변·분석(mock)·완료·조회·삭제의 실제 호출 경로와 기존 검사 범위를 식별하라. API 명세가 이미 있으면 재사용하고 차이만 적어라. 기존 인터페이스에 근거 없이 새 API를 만들지 마라.
1-B. 앱 import/전역 app 생성/Store 생성/테스트 수집 시점의 DB 생성·접속과 환경변수·설정 로딩 순서를 정적으로 확인하라. 필요한 의존성을 먼저 확인하고 프로젝트의 격리된 테스트 환경을 사용한다.
1-C. 앱을 불러오기 전부터 새 임시 테스트 DB와 mock을 선택하는 실행 방법을 확정하라. 팩토리에 DB를 넘기더라도 import 때 기본 DB가 먼저 열리는지 확인한다. 테스트 연결 대상이 생성한 임시 DB임을 검증하고 외부 모델 호출은 발생하면 실패하게 차단한다. 기존 DB를 열어 테스트하지 않는다.

BASELINE.md에 현재 소스·기존 검증·DB 종류·실행 격리 방법·현재 정책과 미결 사항을 기록하라. TASK_RESULTS/01.json에 A/B/C의 개별 상태와 정확한 출력 폴더를 남겨라. 격리를 확인하기 전 앱을 실행하지 말고, 실행 불가 원인은 구체적으로 적어라. 명령2는 시작하지 마라.
```

## 명령 2 — 실제 API 계약과 검증 시나리오 작성

```text
[명령 2/4: API 계약과 검사 기준]
공통 규칙과 명령1의 확정 폴더·BASELINE.md를 읽어라. 현재 구현을 기준으로 프론트 담당자가 연결할 수 있는 API_CONTRACT.md와 API_SCENARIOS.json을 작성하라. 기존 합의 문서가 있으면 출처를 기록하되, 화면을 먼저 만든다는 사실만으로 API 합의가 완료됐다고 쓰지 마라.

2-A. 각 실제 API의 method/path, 인증 쿠키·필수 헤더, 요청 필드의 타입/필수/부재/null, 응답 필드, HTTP 상태·오류 코드를 적어라. 요청 예시는 합성 값으로 작성하고 run/question/answer ID, revision, 답변 버전, idempotency key의 발급·전달·재사용 규칙을 연결한다. 자동 OpenAPI에 빠지는 수동 JSON 검사를 소스에서 보완하라.
2-B. 설문→게임 단계→기본 답변→mock 분석→발생한 후속 질문/답변→완료→조회·삭제의 현행 흐름과 예외 분기를 적어라. 완료·중간 분석·정보 공개·입력 범위·질문 보존은 현재 코드가 보장하는 내용과 정책 결정이 필요한 내용을 구분한다. mock 결과는 의미 분석 품질을 보장하지 않는다고 명시한다.
2-C. 검사 ID별 전제·합성 요청·기대 응답·기대 저장값/변화 없음·근거·필수 여부를 정하라. 정상 흐름 외에 로그인/소유권, 잘못된 자료형·단계·버전, 중복·재시도, 답변 정정, 시간초과·무응답·비교 불가, 완료/삭제 후 동작을 실제 계약에 맞춰 다룬다. 근거 없는 입력 상한이나 정책을 기대값으로 발명하지 마라.

테스트 전 사례는 미실행으로 표시한다. 동작 관찰만 하는 정책 미결 사례는 관찰이라고 적고 요구 충족과 구분한다. TASK_RESULTS/02.json에 A/B/C를 각각 기록하고 명령3은 시작하지 마라.
```

## 명령 3 — 격리한 실제 API·저장 검증과 최소 오류 수정

```text
[명령 3/4: 비AI 백엔드 실행 검증]
공통 규칙과 앞선2개 명령 결과를 읽고, 명령1에서 확인한 격리 환경으로 명령2의 사례를 실제 실행하라. 기존 테스트를 재사용하고 부족한 핵심 사례만 추가한다. HTTP 라우터·인증·Store·DB를 통째로 mock 처리하지 않는다. 실제 라우터를 거치는 인프로세스 HTTP 클라이언트는 가능하며 실서버/브라우저 검사와 구분한다.

3-A. 서로 다른 합성 사용자로 정상 흐름과 각자의 기록 접근 범위를 확인하라. 실제 API 제출 응답뿐 아니라 재조회·테스트 DB 저장값도 확인한다. 새 앱/DB 세션에서의 재조회로 영속성을 확인하라. 삭제는 현행 논리/물리 삭제 계약에 따라 접근·연관 기록 처리를 검사한다.
3-B. 중복/변조 재시도, stale revision, 이전 답변 버전 충돌, 잘못된 단계·입력, 시간초과·무응답, 질문 보존, 완료/삭제 후 요청을 구분해 확인하라. 거절된 요청이 기록을 중복 생성하거나 잘못 갱신하지 않는지 검사한다. 시간 제어는 결정적으로 하고 장시간 대기로 검사하지 않는다.
3-C. mock 분석의 저장·후속 질문·완료 흐름을 검사한다. 기존 지표·기본 근거와 조건부 후속 근거의 구분을 유지하고 AI 미연동 표시를 확인하라. 외부 모델 호출은0회여야 한다. 분석 실패 등 필요한 예외를 주입한 경우 실제 모델 장애 시험으로 표현하지 마라.
3-D. 기존 요구와 충돌하는 재현 가능한 백엔드 오류는 원인·실패 사례를 남긴 뒤 최소 수정하고 해당 회귀·관련 흐름을 재검증하라. 테스트를 코드의 잘못된 결과에 맞춰 바꾸지 마라. 새로운 정책·API 호환성 변경·미선정 기능 후보는 별도 기록한다.

재실행 가능한 테스트와 BACKEND_TEST_RESULTS.json, TASK_RESULTS/03.json에 사례별 기대/실제·성공/실패/보류/미실행·수정 전후·실행 환경·mock/DB 확인 수준을 저장하라. 개인정보·비밀값을 넣지 마라. 필요한 검증을 마치면 숫자를 늘리기 위한 추가 검사를 하지 말고 명령4는 시작하지 마라.
```

## 명령 4 — 프론트 연결 인계와 완료 판정

```text
[명령 4/4: 인계와 최종 판정]
공통 규칙, 실제 수정 diff, 명령1~3 결과를 대조하라. 최종 코드와 다른 API_CONTRACT.md/예시/검사 기대값 설명은 근거에 맞춰 갱신한다. 기존 CSV 설명에 실제 영향을 준 변경만 필요한 범위에서 추적한다.

4-A. FRONTEND_HANDOFF.md에 연결 순서, 실제 요청·응답 예시, 쿠키·필수 헤더, ID/버전·재시도 처리, 진행/누락/오류/mock 상태를 정리하라. 새 프론트의 개발·배포 origin이 정해지지 않았다면 확인 항목으로 적어라. 실제 쿠키·CORS 설정을 기록하고 임의로 전역 허용 설정을 추가하지 않는다. 프론트 코드나 화면을 바꾸거나 담당자에게 메시지를 보내지 마라.
4-B. BACKEND_READINESS.md에서 문서 준비, 필수 API·DB 검증, 오류 수정, 프론트 담당자 합의, 새 UI 통합, 실제 AI, 목표 DB·운영 환경을 따로 판정하라. 이번 준비완료는 확인한 개발 DB+mock 환경의 백엔드 범위다. SQLite 성공으로 MySQL까지 성공 처리하거나 전달안 작성을 담당자 합의로 기록하지 마라.
4-C. 필수 백엔드 사례가 통과하고 명세가 최종 코드와 맞으면 해당 범위 준비완료로 판정한다. 필수 실패·미실행이나 결정이 필요한 핵심 정책이 있으면 그 영향에 따라 미완료/조건부 준비로 판정하고 정확한 다음 작업을 적어라. H-03이나 실제 AI 미연동만으로 이번 백엔드 검증을 실패 처리하지 않는다.

TASK_RESULTS/04.json과 최종 보고에 무엇을/왜 했는지, 바뀐 파일, 재현 명령, 개별 성공·실패·보류, 프론트에 전달할 파일, 남은 선행 조건을 한국어로 적어라. 다른 담당자의 화면 변경·AI 도입·배포로 이어서 범위를 확장하지 마라.
```

## 결과를 다시 검토할 때 필요한 자료

`BACKEND_READINESS.md`, `API_CONTRACT.md`, `FRONTEND_HANDOFF.md`, `BACKEND_TEST_RESULTS.json`을 우선 확인한다. 판정의 재현이 필요하면 해당 테스트·합성 fixture·관련 backend diff와 BASELINE을 함께 제공한다. 기존 감사 자료 전체를 반복 업로드할 필요는 없다.

이 명령서는 실행 지시다. 이 대화에서 현재 사용자 PC의 백엔드를 실행해 준비완료로 판정한 결과물이 아니다.
