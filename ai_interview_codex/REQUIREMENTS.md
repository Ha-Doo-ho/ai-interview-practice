# 제품 요구사항

## 1. 목적과 범위

서비스 이름은 구현 시 기존 프로젝트 명칭을 따른다. 핵심 결과물은 **근거가 얼마나 연결되는지, 무엇이 아직 확인되지 않았는지, 다음에 어떤 경험 설명을 연습할지**를 알려주는 보고서다.

원본 계획서의 텍스트 중심·기록 관리·피드백 방향을 유지하면서, 대화에서 추가된 성향 네 형식과 상황 게임을 MVP에 포함한다. 원래 계획은 학생 2명, 9월 14일~10월 25일의 프로젝트 일정이었다. 이는 당시의 규모·일정 맥락이다. 현재 날짜와 진행 상태를 확인하지 않고 같은 일정이 남아 있다고 가정하지 않는다. 주차·인원·기술 스택은 저장소 현황을 무시하는 강제 설정이 아니며, 작은 팀이 완성 가능한 모듈 구조로 시작한다.

| 포함 | 후속 단계 또는 제외 |
|---|---|
| 네 성향 입력과 원본 강도 보존 | 영상 녹화·ASR·영상 저장은 후속 단계 |
| 자체 제작한 다중 라운드 게임 1개 | 상용 검사의 비공개 규칙 복제 제외 |
| 기본 텍스트 면접과 확인 질문 | 표정·감정·목소리로 성격/진실 판정 제외 |
| 행동 단위 근거 연결, 인용, 연습 방향 | 합격 확률·인성 점수·직무 적합성 자동 판정 제외 |
| 기록 조회·삭제·접근 통제 | 채용 담당자용 자동 탈락·서열화 제외 |
| 합성 테스트·사람 평가 절차 | 근거 없는 정확도 수치 제외 |

## 2. 네 화면의 의미

| 화면 | 기본 입력 계약 | 보존할 의미 | 피해야 할 해석 |
|---|---|---|---|
| 나 알아보기 | `ordinal_6` | 문항에 대한 본인의 동의 단계 | 높은 단계=관찰된 능력/진실성 |
| 타인 관점에서 나 알아보기 | `paired_perspective` | 같은 사용자가 답한 두 관점의 순서형 응답 | 상상한 타인 응답=독립된 동료 평가 |
| 하나만 선택하기 | `bipolar_slider` | 두 끝 사이에서 선택한 방향과 위치 | 모든 문항에서 오른쪽=좋음, 가운데=무응답 |
| 여러 개 선택하기 | `top_k_rank` | 제시 후보 내의 부분적인 우선순위 | 1위가 2위보다 몇 배 강함, 미선택=싫어함 |

UI 이름과 데이터 타입은 따로 저장한다. 나중에 순서 없는 다중 선택을 추가하면 별도 타입으로 정의하며 클릭 순서를 선호 순위로 둔갑시키지 않는다. 참고 화면의 순서 선택과 양극 입력은 구현 방식의 참고다. 시간여행·존경하는 인물 같은 내용을 화면만 보고 행동 역량에 연결하지 않는다.

‘전혀 그렇지 않다 / 그렇지 않다 / 그렇지 않은 편이다 / 그런 편이다 / 그렇다 / 매우 그렇다’라는 순서와 원문을 보존한다. 내부 위치 1~6은 응답 코드다. 코드 차이 2가 심리적 차이 2단위라는 뜻은 아니다. 역문항을 만들 경우 원문 응답과 별도의 검토된 방향 변환 규칙을 보존한다. MVP는 불필요한 역문항 없이 시작할 수 있다.

## 3. 행동 정의와 연결 이유

| 행동 ID | 좁은 정의 | 자체 문항 예시 | 게임에서 볼 수 있는 것 | 면접에서 요청할 근거 |
|---|---|---|---|---|
| B01 | 결정 전에 다른 사람의 정보를 확인함 | ‘공동 결정을 내리기 전에 팀원이 알고 있는 정보를 확인한다.’ | 팀원 정보 열기 기회와 실제 열기 시점, 결정 전/후 | 누구에게 무엇을 물었고 판단에 어떻게 반영했는지 |
| B02 | 제한된 자원을 개인·팀 과제에 배분함 | ‘개인 과제와 팀 과제가 겹치면 목표와 제약을 확인한 뒤 시간을 배분한다.’ | 가능한 배분, 실제 배분, 보상·시간·선행 조건 | 배분 기준, 다른 선택지, 결과 |
| B03 | 새 정보 이후 선택을 재검토·수정함 | ‘새 정보가 들어오면 처음 세운 계획을 다시 검토한다.’ | 새 정보 노출, 수정 기회, 수정 전후 선택 | 어떤 정보로 무엇을 유지/수정했는지와 이유 |

이 표는 **연습용 설계 초안**이다. B01에서 정보 창을 여는 행위는 ‘정보 접근’이라는 대리 지표이며, 상대를 존중하거나 정보를 이해했다는 직접 증거가 아니다. B03에서 수정하지 않은 것도 새 정보와 기존 계획에 따라 타당할 수 있다. 수정 횟수에 무조건 가점을 주지 않는다. B02는 자기 희생을 정답으로 두지 않는다.

AI가 만든 매핑을 자기 승인으로 활성화하지 않는다. 초안 작성과 독립적인 프로젝트 검토를 거쳐 근거·한계가 설명 가능한 매핑만 연습용으로 활성화한다. 이 구현 단계의 검토자는 작성자와 분리된 Codex 도메인 검토 역할일 수 있다. `reviewer_type=ai_agent`와 검토 결과를 기록하며, 전문가 확인을 받은 척하지 않는다. 서브에이전트가 없으면 별도 검토 패스로 작성/검토를 분리하고 그 제한을 기록한다. 사람의 심리측정 검증을 기다려야만 합성 연습 MVP를 만들 수 있다는 뜻은 아니다. `approved_for_practice`는 과학적 타당화가 아니며 `validity_status=provisional_unvalidated`를 별도로 유지한다.

## 4. 자체 게임의 최소 설계

실제 채용검사와 다른 명칭·문항·보상 규칙으로 한 개의 자원 배분 게임을 만든다. 기본 구성은 연습 라운드와 세 가지 조건의 본 라운드다. 연습 기록은 본 라운드 집계와 분리한다.

- 결정 전에 팀원 과제 정보를 열 수 있다. 노출·열기·결정 확정의 순서를 기록한다.
- 한정된 시간/토큰을 개인·팀 과제에 배분한다. 가능한 선택과 보상표를 사용자가 볼 수 있게 한다.
- 이후 조건이 바뀌는 라운드에서는 새 정보 제시와 수정 기회를 기록한다.

라운드별 제한 시간, 정보 열기의 비용 여부, 자원 총량, 선택의 실효 가능성, 새 정보의 내용·노출 시점, 난이도와 순서가 다르면 함께 기록한다. 분자/분모가 명확한 행동 관찰만 집계한다. 게임 내 과제 점수는 그 게임 규칙의 결과일 뿐 협업 점수로 변환하지 않는다.

## 5. 면접과 피드백

기본 질문은 행동별로 중립적으로 묻는다. 여기서 기본 추출의 ‘독립성’은 다른 단계의 분석값을 추출기에 주입하지 않는 입력 분리를 뜻한다. 같은 사용자가 앞선 과제를 경험했으므로 통계적 독립성이나 외부 검증을 보장하지 않는다. 최소 B01~B03을 다루되 각 질문이 모든 루브릭 항목을 물었다고 가정하지 않는다. 경험의 상황·본인 역할·상대 정보 확인·행동·선택 이유·결과·배운 점을 각기 `explicit`, `partial`, `not_mentioned`, `not_asked`, `unassessable`로 구분할 수 있다. `explicit`에도 원문 근거가 필요하다.

기본 추출 후 조건부 질문을 생성한다. 예: ‘이 문항에는 “매우 그렇다”라고 답했고, 이번 과제의 정보 확인 기회 3회 중 1회에서 정보 창을 열었습니다. 두 상황에서 판단 기준이 달랐다면 설명해 주세요.’ 이는 관찰을 확인하는 질문이며 잘못을 추궁하는 질문이 아니다. 질문이 근거를 공개했다는 사실 자체를 기록한다.

면접 답변은 사용자가 진술한 경험이다. 구체적인 답변이라고 실제 발생 사실이 검증되는 것은 아니다. 후속 답변이 앞선 결과에 맞춰 작성될 수 있으므로 독립 증거가 추가되었다고 계산하지 않는다.

보고서의 단위는 행동별 근거 카드다. 각 카드에는 다음이 포함된다.

1. 실제 선택 라벨/방향/순위와 관점.
2. 해당 조건·기회 안에서 관찰된 게임 사실.
3. 면접의 짧은 정확한 인용과 빠진 설명 요소.
4. 비교 상태와 제한, 아직 확인할 질문.
5. 다음 연습에서 보완할 구체적 행동 설명.

예시: ‘자기보고 문항에는 “매우 그렇다”라고 답했습니다. 이번 과제에서는 결정 전 정보 확인 기회 3회 중 1회에 정보 창을 열었습니다. 답변에서는 팀원을 도운 경험을 언급했으나 어떤 정보를 확인했는지는 설명되지 않았습니다. 과제 조건과 실제 경험의 차이를 더 확인해야 합니다. 다음 연습에서는 누구에게 무엇을 물었고 그 정보가 결정에 어떻게 반영됐는지 설명해 보세요.’ 숫자·인용은 실제 기록으로만 채운다.

## 6. 정확도를 높이는 방식

강도 정보를 더 많이 저장하는 것은 정보 손실을 줄인다. 그것만으로 실제 성향 판단 정확도가 높아졌다고 결론 내리지는 않는다. 제품에서 검증할 것은 우선 **저장 충실성, 비교 가능성, 근거 추출의 정확성, 과도한 추론 억제, 연습 제안의 유용성**이다.

동일한 동결 사례에서 강도를 긍정/부정으로 축약한 A와 원래 단계로 보존한 B를 비교한다. 다른 입력·루브릭·모델 조건은 고정하고 조건을 모르는 독립 평가자가 인용 정확성, 근거 없는 원인/모순 판단, 질문의 적합성, 연습 제안의 유용성을 평가한다. 실제 결과·표본·불일치를 보고하고 성격검사의 타당도라고 부르지 않는다. 사람 검토/A-B 평가는 구현 이후 별도 단계로 `pending_manual`을 허용한다. 구현 완료와 효과성 연구 완료를 구분한다.

## 7. 구현과 운영의 수용 조건

회원/세션 인증 방식은 기존 구조를 따른다. 실제 사용자 데이터에는 인증·서버 소유권 검사가 필요하다. 데모는 합성 데이터임을 표시하며 공용 데이터가 개인 기록처럼 보이지 않게 한다. 데이터 사용 목적·삭제 방법을 사용자에게 알리고, 원문·파생값·캐시·작업 결과까지 삭제/무효화 경로를 검증한다.

네 화면·게임·면접·보고서에서 키보드 조작, 선택 상태, 남은 시간, 오류, 재시도, 저장 여부가 이해 가능해야 한다. 기술적인 매핑 버전이나 내부 모델 설정은 사용자가 결과 근거를 확인하는 데 필요한 경우에만 상세 보기로 제공한다.

기계 검증용 요구사항 ID와 수용 사례의 원본 목록은 `HARNESS.md`의 요구사항 표 및 `harness/scenarios.json`이다. 이 문서와 수용 사례가 충돌하면 의미 차이를 먼저 기록·수정하고, 단지 테스트를 통과시키기 위해 제품 원칙을 약화하지 않는다.
